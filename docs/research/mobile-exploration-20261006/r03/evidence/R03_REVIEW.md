# R03 독립 읽기 전용 검토

2026-10-06. 검토 대상: R03 기술/배포/플랫폼/실행 문서, `records/SERVER_COST_UPDATE.md`, R03 evidence의 BENCH_RESULT와 raw JSON, 첨부 벤치마크 harness. 엔진 실행을 재수행하지 않았고 DGX·원본 수정·하위 에이전트를 사용하지 않았다. 현재 공개 가격을 별도 재조회한 가격 감사는 아니다.

## 판정

**실제 PC 엔진의 제한된 실행·저장 왕복 증거와 별도 단순화 시제품 선택은 서로 구분되어 있다. 모바일/서버 실측을 꾸며낸 주장은 찾지 못했다.** 다만 ZIP 발행 전 아래 문구와 증거 연결을 정리해야 한다. 이 문서는 상용 모바일 성능·실제 서버 청구·장기 결정론 승인이 아니다.

## ZIP 전 최소 수정

1. **중간 — wall time을 CPU 점유율로 부르는 한 문장.** TECHNICAL_FEASIBILITY의 `초기 평균×8배 ... 단일 코어시간 약12.5%`는 산술상 1.562×8×10=124.96ms/초이나 입력은 `performance.now()` 경과 시간이다. process CPU 측정이 없으므로 실제 단일 코어 CPU 점유율이 아니다. SERVER_COST_UPDATE의 엄격한 wall/청구 CPU 구분과도 어긋난다. `가정한 실행 경과 시간의 합이 초당 약125ms(직렬 시간 예산의12.5%)`로 바꾸고 CPU 이용률·에너지 측정이 아님을 유지하면 된다. 벤치마크 재실행은 필요 없다.

2. **중간 — 아카이브 내 비용 갱신 문서 연결.** 검토 시점의 `rounds/r03/`에는 SERVER_COST_UPDATE.md가 없지만 DEPLOYMENT_AND_SERVER는 이 파일을 상세 근거로 가리킨다. 이 갱신 문서는 원본 엔진과 $5.80/$55.13 가정 사이의 오독을 막는 핵심 증거다. ZIP 구성에 문서 사본을 포함하고 상대 링크를 아카이브 기준으로 고친다. 기존 갱신 문서의 `../research/PLATFORM_RESEARCH.md`, `BENCH_RESULT.md`, `engine-bench.json`도 ZIP에서 실제 존재하는 경로로 맞춘다. 패키징이 아직 진행 중이라면 현재 중간 상태의 누락이며 최종 전달 결함을 단정하는 것은 아니다.

## 단계3 충족 범위와 남는 제한

- **엔진 재사용:** 원칙/후보 점수/영수증/저장 계약의 재사용과 새 모바일8축·계약·공간전투를 분리했다. 독립 factory, React 연결, 기존 팩 구조 미완성도 드러난다. R04 단순화 모델은 사용자 허용 범위다. 그 성공으로 원본 엔진 이식이나 원본8축 균형을 입증하면 안 된다.
- **현재 틱 비용:** 두 사례의 실제 full advanceTick 440회(예열40+측정400)가 기록되어 있다. 그러나 활성 협상/소송·성숙 영주·연례 처리를 제외한 표본이다. `기술 탐사 완료`는 이 제한된 탐사 납품 뜻으로만 읽어야 하며 제품 타당성 최종 통과로 쓰지 않는다.
- **휴대폰 규모·배터리·발열:** 2/4/8배는 가정이고 12~200명/10~60시설은 실기기 시험 범위다. 이를 가능한 도시 규모의 검증된 상한으로 보지 않는 설명은 적절하다. 사용자 요구 중 실제 중급 Android 전력/열 기반 규모 결론은 여전히 미판정이라는 상태를 R03 요약·R05에도 유지해야 한다.
- **서버 비용:** 단순화한 edge 경로의 단가 산식은 있지만 권고한 원본 Node compute의 `p_instance_hour`가 없어 **원본 엔진 전체 월비용의 달러 범위는 미완료**다. H/slot 민감도는 가격을 대체하지 않는다. 공급사 선택 전 미확정을 솔직히 남긴 것은 허위 정밀값보다 낫다. 이를 R03 결과의 공개 공백으로 명시하면 탐사 ZIP 발행을 막을 필요는 없으며, R05에서 싼 서버비를 진행 근거로 삼아서는 안 된다. 필요하면 후속으로 출처 있는 한 인스턴스 가격을 명시적 예시로 넣되 wall time을 청구 CPU에 곱하지 않는다.
- **오프라인:** 동일 tick100회 진전과 저장 왕복만 확인했다. 이벤트 skip 동등성, 하루치 따라잡기, 서버 동시성은 미검증이라고 명시했으므로 적절하다. PLATFORM_RESEARCH의 경계 적분 제안보다 TECHNICAL_FEASIBILITY의 전체 tick 기준 경로를 구현 우선순위로 삼아야 한다.
- **배포:** 일반 웹→실기기 테스트→PWA/Capacitor 판단이 일관적이다. 설치·서비스워커·알림 미구현을 PWA 완료로 부르지 않는다.

## 확인한 수치·증거

읽기 전용 Node 명령으로 **기존 JSON만 집계**했다. 게임/벤치마크는 실행하지 않았다.

- R03 raw 사본과 records 원본은 byte 동일. SHA256 `8463b38f351c46819c09eba914a422426ef4877a07eec750252f54796e45673a`.
- 초기200표본 평균1.56186791ms, 최대164.01975ms, 50ms 초과2개. 성숙200표본 평균1.153504835ms, 최대2.591458ms. 문서 반올림 수치와 일치한다.
- 두 사례 tick 증가220, 저장 동등성 flag true. harness는 실제 encode/decode 뒤 deepEqual을 실행하며 raw를 신규 경로에 기록한다. flag만 임의로 출력하는 구조가 아니다. 이번 검토 자체가 해당 실행을 독립 재현한 것은 아니다.
- 원본 서버 H 표의 분당/초당60배, k=3 배수, n의 올림 계산은 제시 산식과 일치한다. 4,895,144byte×10k는 약48.95GB이며 월4회/일 로드는 약5,874.17GB로 일치한다.
- 플랫폼 표의 $5.648/$23.69 Workers, $0/$21.25 D1, $0/$2.84 Queues, $0.15/$7.35 R2는 **문서에 주어진 단가·올림 가정**으로 각각 약$5.80/$55.13을 만든다. 이는 현재 공급사 청구 검증이 아니며, 원본 Node 비용으로 재사용할 수 없다.
- RSS 공유 프로세스 값과 isolate128MB의 차이, DAU와 매일 진행하는 전체 계정 A의 차이, warmup/공유 캐시·표본1회 한계가 명시되어 있다. 성숙 fixture가 초기보다 빠른 것을 규모 확장 성공이라고 주장하지 않는다.

수정 범위는 위 두 문서/패키지 정리로 충분하다. 추가 장시간 측정이나 실기기 성공 증거를 R03에 소급 요구하지 않는다. 남는 전력·열·원본 compute 가격 공백을 그대로 전달하는 것이 이번 단계의 올바른 결론이다.
