# S8-R9 결정론적 탐색 예산 (R-9)

## 명세

1. **범위**: 자동 성장의 서비스·시설 및 목책 후보 탐색. 게임의 배치, 서비스 수용량, 도로 통행 규칙은 유지한다.
2. **계산량**: 조언 우선순위별 실제 가상 배정·경로 검사 최대 192회, 한 공동 서비스 배치 탐색의 재귀 분기 최대 12개. 이전 조언의 불가능한 탐색이 뒤의 식량·주택·시대 조언을 막지 않도록 예산을 분리한다. 최대 10개 조언 단계, 총 계측 한도 1,920. 시간은 중단 조건으로 쓰지 않는다.
3. **후보 선택**: 기존 정렬에서 확인한 합법 후보 중 최선의 결과를 유지한다. 확인되지 않은 신규 주택·도로는 채택하지 않는다. 소진 때문에 끝나지 않은 검사 결과를 ‘기존 집이 원래 서비스 불가능’이라는 증거로 캐시하지 않는다. 미래에 채울 수 있는 육지 도로에서도 연결 불가능한 시설 후보는 공동 배치 조합에서 먼저 제외한다.
4. **목책**: 자동 성장에만 보통 둘레/작은 둘레 각각 8개 생성 시도, 중복 경로를 제외한 8개 실제 검사 한도. 수동 추천은 기존 전체 탐색을 유지한다. 후보 캐시 키에 한도를 포함해 자동 성장의 잘린 후보를 수동 추천이 재사용하지 않는다.
5. **진단·저장**: `search_budget_hit`과 실제 사용량/한도를 조언 진단 receipt에 기록한다. GameState·저장 형식은 변경하지 않는다.
6. **결정론**: 서비스 레이아웃 캐시는 매 결정 시작에 비운다. 동일 입력의 따뜻한 캐시·직렬화 복제·새 프로세스 결과가 같다. 목책 경로의 중복 검사 메모는 한 함수 호출에서만 존재하므로 모든 입력이 동일하다.

## 재현과 검증

- S0 `e97d6a8` 자동 성장의 결정 시작 상태 71개 중 실제 `decideNextAction` 스택이 없는 늦은 샘플 2개(48-seed1:142200/143280)를 제외한 **69개 원본**. `fixtures/autoplay-search-budget/manifest.json`에 출처·정책·SHA256을 기록했다. 경제·주민·도로·캐시를 편집하지 않았다. 자연 화면 플레이 증거가 아니다.
- 원본 seed3 tick28,080은 수정 전 12초 watchdog에서 종료되지 않았다. S0 장기 실행은 1,288.23초에도 끝나지 않았다. 가설은 공동 서비스 조합 폭발·투영 도로마다 재탐색·목책 후보별 반복 공급 경로 검사였고, 각각 S0 스택 및 해당 예산 적용 전/후 실행으로 확인한다.
- `tests/autoplaySearchBudget.test.ts`: 계산량 상한, 복제/재호출 결정론, 후속 우선순위 기회, 최선의 완료 결과 유지. 엄격한 1초 성능 판정은 경쟁 프로세스가 많은 전체 단위 테스트에서 하지 않고 아래 독립 직렬 관문에서 실시한다.
- `node --import tsx scripts/autoplaySearchReplay.ts <보고서.json>`: 저장소 내부 아카이브를 임시 폴더에 풀어 SHA를 확인하고 69개를 순차 실행한다. 각 입력은 별도 프로세스, 같은 상태 두 번 호출 일치. seed3-28080은 **1초 미만**, 나머지는 **10초 미만**. 25초 작업자 제한은 검증 하네스에만 있으며 제품 선택에는 사용하지 않는다.
- 최종 69개 측정표는 R1-fix 보고서의 `search-replay.json` 참조. 최초 96회 상한 구현은 67/69였고 목책 후보 생성 두 사례가 남아 별도 생성/검사 한도를 추가했다. 이후 CPU 경합 중 측정은 최종 성능 증거에서 제외한다.

## 캐시 근거·한계

서비스 키는 지형·도로·점유·성벽·시설 운영 중단 상태·배송 가능 공급원 ID를 포함한다. 현재 인력·재고·주택 생활등급은 미래 배치 검사에서 각각 완전 배정·자재 유예·필지 수요로 치환되므로 결과의 독립 입력이 아니다(공급원 자격은 키에 포함). 서로 다른 결정의 부분 검사 결과를 재사용하지 않는다. seed3의 독립 중간 측정은 >12초에서 0.231초로 줄었다. 이는 전체 게임 FPS 측정이 아니다.

예산 소진 시 미확인 후보는 다음 결정까지 보류한다. 최적 배치의 존재를 증명하는 완전 탐색이 아니므로, 시나리오 속도 통과와 별도로 5개 seed 성장 가드레일로 영구 보류가 생기지 않았는지 확인해야 한다.

## 결정 탐색과 별개였던 자연 seed2의 틱 비용

`8fc019f` seed2의 108,000틱 체크포인트 결정은 27.626ms였지만 정상 재생의 113,040틱 부근부터 틱이 느렸다. 120틱 CPU 프로파일에서 `wallReserveHeld → resolveBuildingToConstructionSiteRoute`가 틱 포함 샘플 약96%였다. 56개 건물, 14개 목책 공사장이 있었고 실제 목재 공급원은 하나였으며 선포 당시 비축 목록은 비어 있었다. 기존 진단은 이 경우에도 매 구간·매 틱 모든 건물의 경로부터 조사했다. 실패 경로는 영속 경로 캐시에 들어가지 않아 직접 도로 탐색과 벽 운반 탐색을 반복했다.

새 캐시 대신 동일 자원의 양수 비축 바닥값이 없으면 `false`를 반환하고, 양수 재고가 있는 건물만 경로를 검사한다. 국고는 기존대로 주택 접근 경로를 확인한다. 비축량·배송·통행 규칙과 저장 스키마는 변경하지 않는다. 대안인 실패 경로 메모는 별도 키·메모리 관리가 필요하고 이 입력의 불필요한 조회 자체를 없애지 못하므로 채택하지 않았다.

원본 자연 입력은 `fixtures/construction-reserve/seed2-113040.json.gz`와 출처 파일에 보존한다. 경로 호출 수 회귀 3개는 수정 전 실패했고 수정 후 통과한다(비축 없음/0/다른 자원, 빈 재고, 도달/미도달, 국고). 같은 입력의 정상120틱 평균은 65.180ms에서1.793ms로 감소했고, 최종113,160틱 **전체 GameState가 파생 pathCache까지 동일**했다. 일반 동등성 원칙에서는 파생 경로 캐시를 제외할 수 있지만 이 표본에서는 제외할 필요도 없었다. 측정 중 다른 가드레일이 실행되었으므로 게임FPS 보장으로 해석하지 않는다.

## 자연 seed3 108,000틱 — 불가능한 후보 판정 뒤 다음 행동으로

`00357a7`의 자연 상태를 `tests/fixtures/service-space-capacity/seed3-108000.json.gz`에 출처와 함께 보존했다. 16채가 인구352/수용352, 빵286, 유휴89, 가용 목재23으로 주택 증설 전제를 채웠지만 조언은 `none`이었다. 시장2개 이내로 공동 공급할 수 없는 집 후보(16,17)의 검사를 끝내기 전에 서비스 증명 예산을 소진했다.

`autoplayServiceSpace.ts`는 추가 후 총필지가 시장·교회의 최소수용량24 이하이고 기존 증명의 점유/도로가 영향받지 않을 때만 해당 지역 증명을 재사용한다. 합필은 `houseLotArea`로 세고24→25, 점유·도로 침범, 서비스시설 추가는 기존 재검사를 유지한다. 새집 자체와 도시 전체 공동 공급 계획은 항상 새로 증명한다. 이 재사용으로 기존16집의97+97 재검증을 줄여 공동계획 검사까지168 작업으로 도달한다.

### 완료한 서비스 증명의 결정 간 재사용 — 예산 비용 재청구

가설은 (1) 같은 지형/점유의 지역·공동 서비스 증명 반복이 비용을 지배한다, (2) 완료 증명에 cold 작업량을 기록해 재청구하면 캐시 온도와 결정론을 분리할 수 있다, (3) 정렬한 ID 집합만으로는 검색 순서별 비용을 보존하지 못하므로 실제 입력 순서도 키에 필요하다는 세 가지였다.
