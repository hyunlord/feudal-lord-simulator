# EXT-1 계획 — 닫힌 종류 목록 → 데이터 레지스트리·열린 id

[확장성 설계](extensibility.md) 3절 EXT-1. 관문: 동작 불변(가드레일 해시 그대로, 저장 모양 그대로).

## 조사(2026-10-06, 코드 읽기)
- **정의**:
  - 물자(`RESOURCE_CATALOG`)와 직업(`TRADE_IDS`)은 이미 데이터 배열에서 타입을 뽑는다.
  - 건물(`BuildingKind`, 22종)과 세력(`FactionId`·`FactionKind`)은 손으로 쓴 유니온이다.
- **빠짐없이 적어야 하는 표**(새 종류마다 코드 수정):
  - 건물: `REQUIRED_BUILDER_TICKS`, 건물 목록·문구 표, 시나리오의 "모든 종류 열림" 검사.
  - 세력: `FACTION_PORTRAIT_POOLS`, `FACTION_LEADER_MIN_AGE`, 청원자→세력 표.
  - 직업: 이름 표(문구).
- **불러올 때 검사 없음**: 저장 검사(`assertGameStateSnapshot`)는 건물·공사·재고·직업·세력의 id를 보지 않는다. 모르는 건물 종류는 통과했다가 설정을 읽는 순간 깨진다.
- **접근**: `BUILDING_CONFIG_BY_KIND[...]` 직접 색인이 약 264곳이다(그중 화면·그림 약 1/4). 엔진 코드의 `kind === "mill"` 같은 문자 비교는 약 131곳이다.

## 할 것(엔진 몫만 — 화면·그림 파일은 손대지 않음)
1. **타입은 데이터에서**: 건물·세력 정의를 `as const satisfies` 배열로 하고, `BuildingKind`·`FactionId`·`FactionKind`를 그 id에서 뽑는다(core 팩의 컴파일 안전 유지). 물자·직업은 이미 그렇다.
2. **실행 시 레지스트리** `contentRegistry`: 종류마다 `get(id)`(모르면 분명한 오류)·`has(id)`·`ids()`. 열린 id 타입(`ContentId<"building">` 등)은 레지스트리만 만든다. 엔진의 새 코드는 레지스트리로 읽는다. 기존 직접 색인은 점진적으로 바꾸고, 화면·그림은 렌더가 옮긴다.
3. **불러올 때 검사**: 저장 검사가 건물·공사 종류, 재고 물자 키, 직업 id, 세력 id·종류를 레지스트리로 확인한다. 어느 경로의 어느 값이 왜 틀렸는지 알린다. 콘텐츠 로더(직업 조건의 건물, 등록기의 세력, 시나리오 물자)도 같은 레지스트리로 확인한다.
4. **빠짐없는 표를 정의의 칸으로**: `REQUIRED_BUILDER_TICKS` → 건물 정의의 칸, 세력 초상 풀·지도자 최소 나이 → 세력 정의의 칸. 문구 표(`*.ko.ts`)는 문구 키 작업(EXT-5)까지 그대로 둔다.

## 하지 않을 것(이번에)
- `kind === "mill"` 같은 행동 분기 약 131곳(→ EXT-4 모듈화 때 역할 태그로).
- 화면·그림의 직접 색인 교체(렌더 몫).
- 시대(Era)·필지·지형·청원 종류 등 다른 닫힌 목록(EXT-2·EXT-3 또는 그 체계를 고칠 때).
- 팩 폴더·mod.json(EXT-3).
