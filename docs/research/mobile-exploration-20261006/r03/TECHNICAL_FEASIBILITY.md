# R03 기술 판단: 재사용할 수 있지만 모바일 팩만 넣으면 끝나지 않는다

관문: **기술 탐사 완료, 상용 모바일 성능은 미판정**. 현재 엔진의 작은 실행·저장 왕복을 Mac에서 확인했다. 대규모 실행·DGX·본 저장소 수정·커밋·푸시는 하지 않았다. 원시 표본과 실행 코드는 evidence/ 및 scripts/에 있다.

## R04 구현 선택

**별도 단순화 모델**을 선택한다. 사용자가 허용한 범위이며, 새8축·경제·계약·공간전투의 인과를 빠르게 시험하는 목적이다. 실제 PC 엔진의 성능은 이번 원본 벤치마크로 별도로 판단한다. 시제품 속도를 원본 엔진 속도라고 부르지 않는다.

모델은 순수 상태와 명령/시간 진행, 규칙 정의, 표시를 분리한다. UI와 봇 리그는 같은 모델을 import한다. 축별 이름으로 승률을 직접 조절하지 않고 실제 노동·재고·후보 입지·길·계약으로 차이를 만든다. 브라우저는 모듈을 그대로 실행하고 Node 리그도 같은 모듈을 실행한다. 저장/리플레이에는 판·seed·명령을 남긴다. 기존 PC 소스를 통째로 복사하거나 원본 엔진에 모바일 기능을 삽입하지 않는다.

이 선택의 손실: 실제 PC의 물류·권리·혈통 복잡도, 장기 밸런스, 완성 그림 렌더 품질은 시제품에 그대로 나오지 않는다. 따라서 R04는 ‘차별점의 작동 여부’이지 완성 엔진 이식 증명이 아니다. 향후 공통화는 먼저 두 모델의 명령·읽기 모델 계약을 맞추고, 독립 factory·팩 ID·규칙 버전 경계를 추출하는 순서다.

초기 영주의200표본 중2개가50ms를 넘었다(164.020/120.887ms). 낮은 p95만 보면 이 비용이 사라진다. 같은 구간에 주간 자율성 실행 기회가 있었지만 프로파일을 하지 않았으므로 그것이 원인이라고 단정하지 않는다. 성숙 도시가 더 싸게 나온 것을 인구 증가가 무해하다는 근거로 쓰지 않는다. 서로 다른 시스템이 켜진 두 부하다.

## 중급 안드로이드 규모·전력 예산: 추정과 미확인

실기기 배터리·온도·WebView·GPU는 측정하지 않았다. Mac walltime을 W나배터리%로 변환할 수 없다. 다음은 **2/4/8배 느린 실행환경**이라는 민감도 가정이며 특정 Android 기종의 벤치마크가 아니다.

| Mac 관측 | 2배 | 4배 | 8배 |
|---|---:|---:|---:|
| 초기 평균1.562ms | 3.124ms | 6.248ms | 12.496ms |
| 초기 최대164.020ms | 328.040ms | 656.080ms | 1,312.160ms |
| 성숙 일반p95 1.689ms | 3.378ms | 6.756ms | 13.512ms |

60fps의 전체 프레임 예산16.7ms 중 시뮬레이션 목표를4ms로 잡는 것은 제품 예산 제안이다. 8배 가정에서는 평균도 이를 넘으며, 어느 배수에서도 관측 긴 틱을 메인 스레드에서 실행하는 것은 안전한 선택이 아니다. Worker/서버가 계산하고 화면은 읽기 모델과 보간된 움직임을 그리는 방향을 택한다. Worker도 같은 CPU·전력을 쓰므로 이동만으로 배터리 문제가 해결되지는 않는다.

규모의 현실적인 답은 **모바일 최대 인구를 아직 정할 수 없다**다. 첫 실기기 실험 목표를64×64,12~200명,약10~60시설로 잡고, 화면의 움직이는 인물은 별도의 표시 예산을 둔다. 이는 측정으로 보증한 상한이 아니라 초기 영주 표본과768명 비영주 표본 사이에서 보수적으로 고른 시험 범위다. 768명 영주 도시가 가능하다는 결론은 내리지 않는다. 세 가지 목표 규모에서 주간·계절·연례·활성 협상/소송과20분 체류를 실제 휴대폰으로 비교해야 승인 가능하다.

고정 틱을10회/초 실행한다는 가정에서 초기 평균×8배는 초당 약125ms, 즉 직렬 경과 시간 예산의 약12.5%다. 실제 CPU 이용률을 측정한 값은 아니다. 이는 GPU/화면/네트워크/OS가 빠진 계산량 가정이며 에너지·온도 예측이 아니다. 반면 서버에서 도시를 진행하고 클라이언트는 결과만 보여주면 클라이언트 비용의 중심은 렌더·통신으로 옮겨간다. 해당 비용은 이번 측정에서 미검증이다.

## 오프라인 성장과 따라잡기

검증한 것은 같은 전체 틱100회 반복이 정확히100회 진행하고 저장 왕복이 같다는 것뿐이다. 초기135.388ms, 성숙107.413ms의 작은 묶음이다. 결정론은 같은 입력을 다시 실행할 수 있게 하지만, 수십만 틱을 건너뛰는 계산을 자동으로 정당화하지 않는다.

제품은 서버 now와 lastSettledAt 사이를 고정 규칙 버전으로 정산한다. 한 도시의 명령을 revision순으로 처리하고 결과와 outbox를 같이 확정한다. 장기간 미접속도 수송·계약·사건 경계를 무시해서는 안 된다. 초기에는 동일 틱을 작은 작업으로 잘라 체크포인트를 저장하는 정확한 경로를 기준으로 둔다. 나중에 사건 경계 적분/집계가 필요하면 같은 상태·명령·기간의 전체 틱 결과와 비교해야 한다. 일괄 계산이 다른 규칙이면 전원에게 적용되는 별도 모바일 규칙판으로 공개하고 원 PC와 동등하다고 하지 않는다.

로그인 순간 모든 계산을 동기 대기시키지 않는다. 오래된 읽기 화면에 마지막 확정 시각을 보이고, 큐 정산 완료 후 새 revision으로 갱신한다. 상대 도시를 공격/거래하기 전에는 양쪽의 필요한 논리 시점을 맞춘다. 상호작용할 때만 정산하는 설계는 이웃 의존 그래프 때문에 연쇄 작업을 만들 수 있으므로 realm별 순서·최대 묶음·백프레셔를 둔다.
