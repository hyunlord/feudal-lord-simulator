# Feudal Lord Simulator — 전체 진행 기록

기준일: 2026-09-20 · 제품 작업트리: `feudal-lord-simulator-playable` · 브랜치: `codex/phase15-organic-ground`

제품·검증 기준은 `c70b019`이며 마지막 제품 변경은 `401e9d4`다. 이 문서는 흩어진 제작·구현·검증 이력을 한곳에서 읽기 위한 정리다. 이번 작업은 문서만 추가하며 게임 기능 변경, 새 성능 실험, 전체 테스트 재실행을 포함하지 않는다. 아래 숫자는 각 단계에 보존된 실행 결과다. 개발 브랜치의 GitHub 동기화와 `main` 병합·Pages 배포는 서로 다른 상태이며, 이번 정리는 병합·배포를 뜻하지 않는다.

## 1. 만들고 있는 게임

시저 3처럼 길과 시설을 직접 배치하고 주민·운송·생산을 연결해 작은 정착지를 성곽 도시로 키우는 중세 도시 건설 게임이다. 등각 시점, 읽기 쉬운 도로, 작은 주민과 수레, 주거·생산·시장·방어 구역의 구분이 핵심이다. 로마 건축을 옮기는 것이 아니라 중세 유럽의 마을을 만든다.

아트 작업 기본값은 잉글랜드 남부·남동부 약 1300–1450년, 프로필 `S_England_1300_1450_v1`, 기준 `AB_2026-09-19_v1`이다. 집의 발전은 같은 시대의 도시화·상업화·층수·돌출층·가게 전면 차이로 표현한다. 목골조·따뜻한 회칠·낮은 잡석 기단, 외곽 초가와 성벽 안 평기와를 사용한다. 주택을 목재→벽돌→석조의 재료 사다리로 올리거나 근세 건축으로 바꾸지 않는다. 기본 주택의 굴뚝 통·푸른 반사 유리·슬레이트·둥근 기와는 제외한다.

도시는 기존 강·다리·시장과 옛 마을의 흔적을 유지하면서 확장하는 방향이다. “성을 크게”는 성채 확대뿐 아니라 성곽 안에 자유롭게 건설할 넓고 평탄한 땅을 남긴다는 뜻이다. 완성된 장식과 숲으로 빈 땅을 다시 채우지 않는다.

원본 아트 바이블은 별도 제작 작업트리의 `docs/art-direction/AB_2026-09-19_v1.md`에 있다. 위 방향은 그 제작 기준의 요약이며, 해당 파일이 이 제품 저장소에 올라와 있다는 뜻은 아니다. 제품에 보존된 아트와 설치 근거는 [승인 아트 기록](asset-evidence/accepted-art/integration.json), [제품 현황](DEVELOPMENT_STATUS.md), [Phase 16 아트 기록](verification/phase16/F3-art.md)에서 확인한다.

## 3. 현재 서로 연결되어 작동하는 시스템

| 시스템 | 구현과 플레이 결과 | 경계 |
|---|---|---|
| 배치·도로 | 길·건물 점유 충돌 방지, 건물/공사장과 성벽 최소 한 칸 간격, 전체 합필 면적 검사 | 기존 불법 저장 배치를 자동 이주시키지는 않음 |
| 생산·인력 | 주민 기반 노동력을 배분하고 길·원료·일꾼·출고 공간을 확인 | 모든 시설이 동시에 무제한 가동되지 않음 |
| 물류·공사 | 출발 재고와 도착 공간 예약, 실제 수레 이동, 공사 자재 배송·인력, 취소/단절 시 예약 정리 | 고립 시 논리적 자원 반환과 물리적 귀환은 구별 |
| 식량 | 농장→방앗간→곡창→배급원이 주택에 빵 공급 | 시장이 빵을 배달하는 구조가 아님 |
| 서비스 | 우물 12·시장 24·교회 32필지 수용량, 거리·도로·인력 조건 | 주민 개인별 쇼핑·예배·급수 방문 시뮬레이션은 아님 |
| 주택 | 물·빵·곡창·시장·교회·완성 성벽 보호에 따라 L0–L4 발전 | 서비스 회복 뒤 별도 승급 공사는 없음 |
| 합필 | 같은 생활·건축 단계의 두 집을 2×1 또는 1×2 단일 건물로 결합 | 자동 연쇄 합필·2×2·분할·PNG 자유 회전은 아님 |
| 퇴화·복구 | 생활등급과 최고 건축단계를 분리하고 상태 레이어/상세창에 악화 표시 | 집 구조가 서비스 하락만으로 초가집으로 바뀌지 않음 |
| 자동 개발 | 도로 복구, 부족 서비스 확장, 식량 체인과 실제 운송거리 고려 | 임의 도시의 전역 최적 배치·물류를 보장하지 않음 |
| 경제 연결 | 연결 창고의 잉여 판매와 필요한 교회 공사 자재 보호 | 세금·임금·수리비 경제를 새로 추가한 것은 아님 |
| 가림·선택 | 도로를 입체 물체보다 먼저 그림, 일반 건물 불투명 유지, 뒤집 선택 지원 | 정상 앞벽 가림 유지, 전역 윤곽 모드는 별도 |

서비스 수용량은 인구 수가 아니라 필지 수다. 합필은 두 필지이며 빈집도 자리를 유지한다. 이용 가능한 공급자가 적은 집부터 배정하지만 임의 네트워크의 전역 최적 배분 증명은 없다. 시장의 일꾼 3명과 연결 도로, 교회의 연결 도로 조건을 유지하며 교회 일꾼 0 정책도 유지했다. 근거: [도시 시스템과 제한](TOWN_SYSTEMS_V2.md), [설계 결정](DECISIONS.md), [승리 조건](verification/phase16/D-victory.md).

## 4. 아트·지면·건축 표현의 현재 상태

- 승인된 단독 L3는 **v2**다. 반려된 v3나 Phase 16의 새 L3/L4 비교 후보로 교체하지 않았다. 기존 ID와 원본을 보존하고 설치본·파생본을 구분한다.
- 초기 승인 원본 25장은 저장소 내부에 보존되어 인접 아트 폴더 없이 검증할 수 있다. 이전 합필 원본도 이력으로 남기고 실제 사용 파일은 현재 매니페스트로 확인한다.
- Phase 16에서 런타임 이미지 73종을 축소하되 저작 좌표·접지 기준은 유지했다. 타일링 흙은 일반 스프라이트 축소에서 제외했다. HTTP 상태·크기·SHA 일치를 검사했다.
- 농지는 흙과 작물을 분리하며 기존 정사각 필지와 재질 반복의 흔적은 남는다. PNG를 교체했다고 유기적인 자유형 필지가 구현된 것은 아니다.
- 관리 상태 33종은 세 모티프를 본체별 좌표에 등록한 파생 레이어다. 독립 생성 이미지 33장으로 집계하지 않는다. 퇴화/복구 시 실제 출력과 제거를 검사했다.
- 넓은 석벽 안 빈 잔디의 채소밭·과수·목초지는 최대 타일 밀도 6.25%의 경관이다. 생산·점유·통행 효과가 없고 길을 놓으면 사라진다. 자연 저장 도시에서는 안전한 넓은 영역이 없어 0개였으므로 통제 배치 화면을 자연 발생 증거로 쓰지 않는다.
- 성벽은 양축·대각·접합·윗면의 석재 언어를 맞췄다. 격자 계단 윤곽을 임의 대각선으로 줄이지 않았으며 성문 대체 그림의 회색 윗면은 남는다.

## 5. 도시 성장과 승리를 어떻게 확인했는가

초기 우선순위 작업은 인구 176·석벽 19/19와 기존 승리를 확인했지만 시장은 여덟 집 모두 거리 밖이고 교회는 없었다. 이 결과를 “모든 서비스와 L4까지 완성”으로 해석하지 않았다. 후속 도시 시스템에서 시장·교회 연결, 자재 판매 보호, 식량 시설의 실제 도로 거리, 서비스 확장을 수정했다.

도시 시스템 v2는 정상 기본 상태에서 415,877틱까지 자동 개발·reducer·엔진으로 성장시켰다. 여덟 집 L4·총 256명·물/시장/교회 8/8을 확인하고 추가 식량 관찰을 포함해 403,877–427,877의 연속 24,000틱 안정성을 기록했다. 전체 성장 시간을 브라우저 클릭으로 재생한 것은 아니다. 실제 UI는 자연 엔진 저장 상태를 불러와 표시·조작을 확인했다.

Phase 16은 승리 조건 자체를 보강했다. 기존 번영 조건에 **입주한 L4 주거 네 필지**를 추가하고 합필은 두 필지로 센다. 기본 seed 1에서 400,129틱에 기준을 충족하고 1,200틱 연속 유지 후 401,328틱에 승리했다. 최종 24,000틱 동안 인구 256·L4 여덟 가구·서비스 8/8·가구 최소 빵 8을 유지했으며 빵 0틱은 없었다. 안정 구간 이전 한 차례 조건 중단의 원인은 별도 특정하지 않았다. 단일 seed 결과를 임의 도시나 무한 시간 안정으로 일반화하지 않는다.

길 단절은 엔진과 UI에서 따로 검사했다. 도시 시스템 v2에서는 도로 세 개 삭제 뒤 시장·교회가 끊기고 401틱 후 생활 3/건축 4로 내려갔다. 복구 23틱 후 새 배급과 생활 4 복귀를 확인했다. Phase 16에서는 실제 초기 플레이의 생활 L3→L1/건축 L3→L3와 등록 상태 그림 출력·제거를 별도로 검증했다.

## 6. 성능 개선: 단계별 결과와 실패한 가설

아래 측정은 **각 단계의 기준과 후보를 따로 비교**한 것이다. 서로 다른 실행의 비율을 곱해 전체 개선율을 만들지 않는다. 렌더 측정은 주로 동일 인구 176 도시, Apple M4 Max, Chrome 153, 1600×1100, DPR 1/2 조건이며 다른 기기나 배포 성능을 보장하지 않는다.

| 단계·작업 | 기준 → 후보 관찰 | 판정 |
|---|---|---|
| 초기 성벽 래스터 재사용 | 당시 실제 UI 진행 중앙값 199.9→66.6ms | 당시 장면 개선; 이후 단계와 연쇄 비율 계산 금지 |

Phase 16 A의 첫 DPR1 이동 측정은 악화처럼 보였으나 실행 순서를 뒤집자 방향도 반전했고 평균 차이는 작았다. 지속적인 개선·회귀나 반짝임 제거를 주장하지 않는다. C의 기준 도시는 시장 거리 조건에서 제외되는 집이 많아 연결 질의 자체의 개선이 전체 틱 개선으로 이어지지 않았다.

초기 CPU 프로파일은 농지 흙의 `drawImage`를 가리켰지만 흙 패턴 캐시 실험은 비용을 다음 이미지 출력으로 옮겼을 뿐 프레임을 개선하지 못해 반려했다. 출력 패스를 분리한 진단에서는 지형 패턴 클리핑을 제거할 때 개선되어 직접 채움으로 전환했으며, 이 판단과 반려 이유는 제품 커밋 `d08f572`에 기록되어 있다. Phase 17은 동일 마름모를 반복 clip/save/restore로 처리하던 지형을 직접 패턴 채움으로 바꿨다. 이미지·점유·길찾기·시뮬레이션을 바꾸지 않았고 성벽 윗면/일반 접합부의 재질도 함께 맞췄다. 정식 비교는 `bd0890a`→`d08f572`이며 재질 변경만의 독립 속도 향상은 주장하지 않는다.

Phase 18은 `EraConsole.tsx`의 목책 초기 제안을 촌락 시대에만 계산하게 했다. 새로운 캐시 없이 조건으로 계산 범위를 줄였다. 목책·석조 시대에서 모델 100호출당 제안·점유 계산 100→0회, 촌락은 100→100회를 확인했다. 정식 비교는 `e05b46c`→`401e9d4`다. 모델 평균에 큰 이상치가 있어 그 개선 비율을 대표 성능으로 쓰지 않으며 무계측 프레임 실험과 분리한다.

Phase 17의 **기본 GPU 240조합 엄격 픽셀 안정성은 미충족**이다. 기준·후보 모두 반복 readback에서 도로 픽셀이 변했다. 실패 시 Canvas 스택·clip·alpha·합성·변환이 정상이고 도로 fill이 매번 실행되어 상태 누수나 도로 그리기 생략 가설은 지지되지 않았다. CPU readback 진단은 양쪽 240조합과 반복 검사에서 차이 0이었지만 기본 GPU 통과를 대신하지 않는다. 실제 화면에서 새로운 도로 소실은 관찰하지 못했으며 제품 Canvas 설정도 변경하지 않았다.

## 10. 다음 작업의 우선순위

1. **플레이 화면의 읽기·조작 문제**: 작은 글씨와 하단 잘림을 실제 화면 크기별로 재현하고 메뉴·선택·키보드 동작을 보존하며 수정한다. 미적 개선과 기능 검증을 함께 판단한다.
2. **GPU 반복 출력 원인 분리**: 현재 기준/후보 양쪽에서 발생하는 readback 차이를 작은 재현으로 줄인다. CPU 모드 진단을 제품 해결로 대체하지 않는다.
3. **게임플레이 검증 범위 확대**: 여러 seed, 수동 건설, 서비스 수용량 경계, 길·문 차단과 복구를 확인한다. 현재 단일 seed 안정 결과를 출발점으로 삼는다.
4. **성벽·지형의 남은 시각 문제**: 격자 계단, 성문 윗면, 필지/재질 반복을 점유·길찾기와 맞춰 개선한다. 그림만 대각선으로 당겨 논리 장벽과 어긋나게 만들지 않는다.
5. **실측에 따른 다음 성능 작업**: 다른 기기·큰 도시와 DPR2의 병목을 다시 측정한 후 범위를 정한다. 새 캐시를 먼저 늘리거나 기존 수치로 60FPS를 약속하지 않는다.
6. **후속 아트·기능은 별도 범위 유지**: L3/L4 비교 후보, 방향별 전면, 자유곡선 도로, 2×2 합필, 대형 항구·새 생산망은 현재 완료 항목으로 올리지 않는다. 승인 원본 보존과 실제 설치 증거를 유지한다.

이 순서는 남은 문제의 우선순위 제안이며 이번 문서 작업에서 실행·일정·배포를 약속한 목록은 아니다. 제품 코드와 증빙은 개발 브랜치에서 관리하고, 공개 배포 여부는 별도로 확인한다.
