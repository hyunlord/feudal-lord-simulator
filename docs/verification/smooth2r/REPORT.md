## 1. 먼저 잰 것 (본선 `aca211e7`, 이 Mac의 Chrome 창 1600×882 · DPR 2 · 줌 2, 가장 큰 도시 `fixtures/perf-gate/ch4-1380`)
기록: [`probe/trunk-aca211e7-probes.json`](probe/trunk-aca211e7-probes.json)(임시 계측, 커밋하지 않음).

- **지면 청크가 왜 다시 만들어지나**
  - 5× 1분: 청크를 다시 그리게 한 것은 계절 표시(한 번, 90 ms 안) 하나뿐. 날씨·시각·커서 같은 매 프레임 값은 청크 열쇠에 없다(열쇠 = 그리는 지형·길·구역·밭 줄의 해시 + 그림 준비 비트 + 계절 + 줌).
  - 1× 3분(계절 한 번): 새 2052×1028 캔버스 111장 = 계절 미리 준비 42 + 섞기(블렌드) 42 + 둘레 미리 그리기 27. 곧 계절 전환 한 번에 새 캔버스 84장(약 700 MB)을 만들고, 섞기가 끝나면 옛 42장을 버렸다. 밭 줄의 작물 단계가 바뀐 청크 13개는 실제 지면 변화.
  - 청크 59장 = 화면의 약 42장 + 화면 밖 17장. 줌 2·DPR 2에서 한 장 8.4 MB라 화면에 보이는 것만 약 353 MB.
- **걷는 사람 합성이 왜 반복되나**: 열쇠(몸 그림 | 든 것 | 겨울 망토)에 매 프레임 바뀌는 값은 없다. 지도에 보이는 생김새가 81(5× 1분)~113(1× 3분)가지인데 칸이 64라서 가장 오래된 것부터 밀려나고 곧 다시 합성됐다(1분 합성 270·내보냄 206, 합성 한 번에 캔버스 9장).
- **getTransform**: 그림마다(걷는 사람·벽·건물·밭·아이콘…) 한 번씩 — 프레임당 520번(헤드리스 1280×800에서 초당 31,119; SMOOTH-G 창에서 71,000).
- **실행 중 getImageData**: 불러온 뒤 30초 169번 1,175 ms, 카메라 20초 1,723번 2,900 ms(벽 래스터 여백 자르기가 거의 다).

## 2. 고친 것
1. **메모리 예산 관리자** `src/render/canvasBudget.ts`: 모든 캔버스 캐시(지면 청크, 걷는 사람 칸, 그림 래스터, 그림 축척 사본)가 바이트로 등록, 합계 상한 400 MiB. 넘으면 빈 캔버스 풀 → 다른 계절(미리 준비한 것) → 다른 줌 → 화면 밖 → 오래 안 쓴 것 순서로 내보낸다. 지난 두 프레임에 그린 것은 내보내지 않는다. 버리는 캔버스는 풀로 돌아가 같은 크기의 다음 요청이 다시 쓴다.
2. **지면 청크** `groundChunkCache.ts`: 다시 그릴 때 자기 캔버스에 그린다(크기가 바뀌면 풀에서). 계절 전환은 청크마다 제 순간에 새 계절로 바뀌는 물결(나무·지붕과 같은 방식, `seasonForObject`) — 섞기 캔버스가 없다. 다음 계절 청크 미리 준비는 예산에 자리가 있을 때만(줌 1이면 들어가고, 줌 2·DPR 2 창에서는 자리가 없어 제자리 다시 그리기). 다시 그리기는 프레임당 4 ms 예산, 그동안 옛 청크를 보인다. 블릿은 지형 단계가 한 번 읽은 변환을 쓴다.
3. **걷는 사람 칸** `walkerComposer.ts`: 열쇠 = 몸 | 든 것 | 망토 | 방향 + 걸음 프레임 → 108×108 캔버스 하나. 같은 생김새는 한 장을 같이 쓴다. 칸 수 상한은 없고(보이는 생김새만큼), 10초 동안 아무도 그리지 않은 칸은 풀로. 합성용 큰 캔버스와 ImageBitmap 옮기기는 없앴다. 불러올 때·장이 바뀔 때 지도의 생김새를 한가할 때 미리 합성(`walkerWarmup.ts`). 수레는 런타임 배우 적재기가 불러올 때 이미 래스터한다.
4. **getTransform 한 번** (하위 작업): `drawCroppedWorldSprite`는 맞춤(snap)할 때만 변환을 읽고 인자로 받을 수 있다. 물체 단계는 줄 세운 뒤 한 번 읽어 벽·걷는 사람에 넘긴다.
5. **빌드 때 픽셀 사실** (하위 작업): `scripts/buildPixelFacts.ts` → `pixelFacts.generated.ts`. 벽 래스터 여백은 그리기를 기록해 계산(`rasterDrawBounds.ts`, 그림은 빌드 때 불투명 경계), 나무 색조는 없앰(색조가 바꾸는 픽셀 0), 비 무리·눈송이·날씨 평균색은 빌드 때 값. 실행 중 `getImageData`는 문장 그림(`EmblemImage.tsx`, 카드가 처음 문장을 보일 때 한 번, 캐시) 하나만 남았다.
6. **배치 끌기** (하위 작업): 마우스 이동은 저장만, 프레임 시작에 마지막 입력 하나를 처리(누름·뗌·휠 등은 먼저 비움 — 뗄 때 마지막 입력으로 놓는다). 예측 패널의 같은 높이 설정 제거. 
7. **지면 경계 재구성 나누기** (하위 작업): 바뀐 지면 장면을 단계별 생성기로 프레임당 4 ms 안에서 짓고, 끝날 때까지 옛 장면(옛 청크)을 보인다. 결과는 한 번에 지은 것과 같다(시험).

| B | 판정 아님 245.3 | 통과 23.6 | 실패 1,501.6 |

- B도 1.5초 프레임을 낸다 → 지면 청크 변경이 원인이 아니다. 두 쪽의 가장 긴 프레임(A2 1,698 ms, B3 1,675 ms)은 같은 모양이다: UI 채널의 `publish`(setTimeout → React 다시 그리기) 560~674 ms + `drawFrame` 542~569 ms + `runFrame` 84~145 ms, 계절 결산 창이 열리는 무렵. 추적한 1,901 ms 프레임(가지 15.1초)은 지면 청크 블릿이 GPU를 460 ms 기다리고 React 예약 292 ms·강제 레이아웃 178 ms가 겹쳤다.
- 그래서 청크 변경은 살리고, 계절 결산 무렵의 UI 한 번 튐은 다음 작업으로 뗀다(아래).

## 결정
- SMOOTH2R-D1: 캔버스 예산 400 MiB 하나(지시서의 예). 화면에 보이는 것(지난 두 프레임)은 넘어도 내보내지 않는다 — 줌 2·DPR 2 창에서 지면 청크만 약 338 MiB라 그 밖이 먼저 비워진다.
- SMOOTH2R-D2(사용자 판정 대기): 지면의 계절 전환을 섞기(크로스페이드)에서 청크별 물결로. 두 벌의 캔버스(미리 준비 + 섞기, 약 700 MB)를 없애기 위해서다. 1×에서 1.5초 동안 청크 경계를 따라 옛 계절과 새 계절이 잠깐 나란히 보인다.
- SMOOTH2R-D3: 걷는 사람 칸은 개수 상한 없이 보이는 생김새만큼, 10초 안 그린 칸은 풀로(옛 관문 5의 25 MB 상한 대신 예산 관리자).
- SMOOTH2R-D4: 나무 색조 제거 — 빌드 때 세어 보니 색조가 바꾸는 픽셀이 0(여섯 나무·여섯 톤, Chrome에서 확인).
- SMOOTH2R-D4에 함께: `EmblemImage.tsx`의 `getImageData`는 남긴다(프레임 밖, 결과 캐시, 합성기를 다시 써야 해서).
- SMOOTH2R-D5: 병합은 1단계 전체 대신 회귀 없음(SG4) — 사용자 판정. 1단계 전체는 REMOTE가 조용한 Mac에서 잰다.

## 남은 것
- **계절 결산 무렵 한 번의 튐**(가지·본선 청크 둘 다): UI 채널 `publish`가 React 전체를 다시 그리는 600 ms 안팎 + 그리기 550 ms. 계절 장면 A 3번 중 2번, B 3번 중 1번(판정 아님 하나 제외). 다음 작업.
- **페이지 밖 대기**: 스크립트가 거의 없는데 그리기 시작 전 70~210 ms 기다리는 프레임(GPU·합성기), 본선에도 있다.
- 길 놓기 프레임은 여전히 80~100 ms(장면 짓기 밖, 추적하지 않음 — 청크 다시 그리기 추정).
- 가장 큰 도시 저장에서 봇이 60초 동안 짓지 않아, 장면 나누기는 길을 직접 놓아 쟀다.
- 틱마다 GameCanvas가 다시 그려지는 경우(도구를 든 채 건물 위에 있을 때)는 호버 의미가 바뀌는 일이라 두었다.
