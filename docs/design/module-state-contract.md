## 1. 계약 후보

`GameState.modules`는 모듈 ID별 슬롯이다. 각 슬롯은 `{version, packId, packVersion, data}`를 갖는다. 슬롯 존재가 활성 상태이며, 없으면 기존 동작을 보존한다. 후보 ID는 `core:mediation`, 데이터 판은 1, 팩 표지는 `core` / `prototype-1`이다. 알 수 없는 모듈·팩 표지·미래 판·잘못된 데이터·끊어진 소송 참조는 저장을 읽을 때 거부한다. 구형 저장 v54는 v55로 이행하되 상태에 빈 슬롯을 억지로 쓰지 않는다.

저장 전체 판과 모듈 데이터 판은 별개다. 이 실증에는 과거 모듈 데이터가 없으므로 v1 이전 데이터 이행을 꾸며 넣지 않았다. 향후 각 모듈이 버전별 이행을 제공하고 엔진이 순서·실패의 원자성을 관리해야 한다. 현재 디스패처는 단일 등록 모듈이며 동적 코드 로더·의존 해결·팩 설치 화면을 구현한 것은 아니다.

근거는 `docs/design/extensibility.md` 2절의 코어/모듈/팩, 원칙 1·3·6 및 EXT-3/4다. **EXT-3 전체 완료 선언이 아니다.** 슬롯의 팩 표지와 검증을 실제로 통과시켰지만 실제 `mod.json` 로딩·다중 팩 의존성·패치 병합은 후속 엔진 계약이다. EXT-4는 해당 소송 절차만 점진적으로 연결한다. 코어 소송과 수입 함수는 사건 ID를 알지 않는다.

## 1.1 공식 채택용 제안 인터페이스와 결정론

아래는 **이번 단일 모듈 실증에 아직 구현하지 않은 구체적 계약 제안**이다.

- 호스트 등록 정의: `{id, apiVersion, stateVersion, ownerPack, validate, migrations, commands, readModels, hooks}`. `commands`는 이름공간 명령 ID → 입력 파서/권한 검사/순수 상태 전이/성공 영수증, `readModels`는 이름공간 읽기 ID → 입력 파서/읽기 함수로 등록한다. 외부 명령은 `{moduleId, commandId, actorId, requestId, args}`로 수신하며 actorId는 호출자가 임의 대리하지 못하도록 엔진 경계가 확인한다. B는 모듈 내부 구현을, 엔진은 등록/권한/원자적 실행을 소유한다.
- 모드 폴더의 `mod.json.modules`는 같은 등록 ID를 선언한다. 호스트가 승인한 코드 등록부의 공개 API 판과 일치하는 정의만 로드한다. core도 그 길을 쓴다. 임의 JS 평가나 별도 본편 저장 통로를 두지 않는다. 모듈 누락·중복 ID·팩 판 불일치·의존 누락이면 플레이를 시작하지 않는다.
- 갈고리 메타데이터는 `{phase, priority, moduleId, resourceKind}`다. phase의 고정 순서는 `beforeSuitStep → estateIncome → afterSeason`이며, 같은 phase는 정수 priority 오름차순, 다음은 moduleId의 UTF-8 바이트 오름차순이다. 객체 삽입 순서·파일 탐색 순서·현재 언어 locale에 의존하지 않는다. 동일한 입력과 같은 명령/등록 목록은 같은 호출 순서와 상태 바이트를 만든다.
- 충돌은 단순히 마지막 작성자가 이기는 방식으로 처리하지 않는다. 같은 소송에 둘 이상의 종료/유예 소유자가 걸리거나 같은 수입 영수증의 동일 몫을 두 모듈이 청구하면 해당 거래를 **변경 전 상태로 전부 거부**하고 양쪽 모듈/계약 ID를 오류에 담는다. 읽기 갈고리는 함께 허용하되 금전/소송의 배타적 자원 키는 호스트가 검사한다. 한 거래에 이미 처리된 requestId/수입 영수증 ID는 재실행하지 않는다.
- 공개 읽기 함수는 mutation을 반환하지 않는다. 모듈에 `GameState` 전체 쓰기 권한을 주기보다 소유 슬롯 쓰기와 명시적 호스트 효과(소송 유예/종결, 금전 게시)를 돌려주는 결과형을 공식 API로 삼는다. 이번 실증은 기존 엔진 함수 서명과 연결하기 위해 순수 `GameState → GameState`를 쓴다.

## 1.2 모듈별 이행과 실패 원자성 제안

엔진은 먼저 팩 목록/판/API와 활성 모듈 집합을 확인하고, 입력 저장을 복사한 임시 상태에서 전체 저장 이행 및 모듈별 `n → n+1` 이행을 실행한다. 각 모듈은 연속 판의 순수 함수와 판별 스키마를 제공한다. 누락 단계·미래 판·스키마/참조/원장 불일치가 하나라도 있으면 입력 파일·실행 상태를 변경하지 않고 모두 거부한다. 성공할 때만 새 상태를 공개한다. 모듈 이행 순서는 의존 모듈을 먼저 두는 위상 순서로 고정하고, 동시에 실행 가능한 모듈은 ID의 UTF-8 바이트 오름차순으로 정한다. 의존 순환은 실행 전에 거부하며 이행 도중 시간·난수·파일 I/O·다른 모듈의 직접 쓰기를 금지한다. 최종 모듈 키도 바이트 순으로 직렬화한다.

수입/소송에 쓰기 가능한 두 모듈의 충돌 거부, 실제 n→n+1 모듈 이행 중 실패 때 원본 바이트 보존, 등록 순서가 뒤집혀도 동일 상태 해시, 제거된 활성 모듈 복구 거부가 공식 채택의 추가 시험 관문이다. 현재 실증은 v54→v55 전체 저장 이행과 단일 모듈 v1 스키마/미래판 거부까지만 구현했다.

## 1.3 기록 압축·종료 표지 제안

미결 절차와 잔액이 1 이상인 예치는 항상 전체 상태를 보존하고 일반 발생 목록의 길이 제한으로 자르지 않는다. 종료되고 잔액이 0인 계약의 상세 기록은 모듈별 최근 256건만 활성 목록에 두며, 오래된 것은 별도 영속 archive에 `{contractId, suitId, parties, outcome, closedTick, received, released, lastReceiptId}` 종료 표지로 압축한다. 종료 표지는 판 전체 동안 유지하여 같은 ID의 재제안·지급 재실행을 거부한다. 256건은 **검토용 제안 값**이며 이번 코드의 측정/구현 값이 아니다.

활성 계약 수나 archive 크기가 예산을 넘으면 새 계약 생성에 명시적 거부를 돌리고 기존 계약/돈을 지우지 않는다. 계약 종료 표지, 장부의 fundId별 합, 원천 영수증의 중복 방지 표지를 함께 저장/이행한다. 이 실증의 cases는 아직 삭제/압축하지 않으므로 장기 증가량을 제한한 구현이라고 주장하지 않는다.

## 2. 135의 실제 상태 전이

`mediationCommand`는 제안, 각 당사자의 개별 동의, 각 당사자의 종결 동의, 별도 예치 제안/동의/해제를 받는다. 제안은 동의가 아니다. 같은 소송의 중복 제안·같은 당사자의 중복 동의·제삼자 동의·기한 뒤 동의는 상태를 바꾸지 않는다.

대상은 기존의 전체 영지 소송이며 filed/evidence/patronage/hearing 중 하나다. 중재자는 실제 인물 목록의 생존 성인이고, 이탈하지 않았으며 영주 가솔·당사자 개인·당사자 세력 수장/구성원·대상 영지의 가문 구성원이 아니어야 한다. 이 검사는 현행 인물·가문·세력의 신원으로 판정한다. 보이지 않는 정치적 이해관계까지 중립임을 입증한다는 뜻은 아니다. 이후 사망/부적격이면 유예를 해제한다.

- `estateSuits.advanceSuits`는 계절 첫 진행에서 모듈 판정을 **판결과 비용 청구 전에** 받는다.
- 양측 동의가 있으면 실제 소송 진행·비용을 건너뛴다. `stageSince`·후원 점수는 변경하지 않는다.
- 기한은 배타적이다. 경계 시각이 기한 이상이면 만료하고 원래 소송을 재개한다.
- 양측의 별도 종결 동의가 있으면 다음 기한 전 계절 경계에서 소송을 closed, 청구를 lapsed로 끝낸다. 판결 승자를 만들지 않고 권원·점유를 옮기지 않는다.
- 기존 `suitActions.nextStageTick`도 유예 기한을 반영한다. `mediationCases`가 계약·당사자·기한·동의·예치 상태를 읽기 전용으로 돌려준다.

`seekSuitPatron`은 관계 점수를 후원력으로 더하는 기존 기능이다. 중재에 재사용하지 않았다. `settleSuit(pay/yield)` 역시 영주 피고의 권원/점유 변경 기능이므로 재사용하지 않았다. 135의 실제 영주 원고가 patronage까지 기존 함수로 진행한 뒤 중재로 멈추는 시험을 포함한다. 정본 사건 데이터와 활성 목록은 그대로다.

## 3. 실제 수입 예치

예치는 중재 동의와 별도다. 당사자 둘이 보관자, 분쟁 몫 비율, 합의종결 뒤 영주에게 돌려준다는 해제 조건을 각각 수락해야 한다. 보관자도 실제 독립 성인 판정을 통과한다. 금고에서 돈을 빼서 수입을 예치한 것처럼 꾸미지 않는다.

`stewardship.estateSeason`이 실제로 계산한 착복·오류 차감 후 `reported`를 게시하기 직전에 나눈다.

`reported = cash 게시액 + restricted 게시액`

분쟁 없는 몫은 금고로, 합의한 몫은 `restricted`의 계약별 `fundId`로 게시한다. 계약 상태에는 balance/received/released/lastIncomeTick를 보존한다. 같은 영지·같은 계절 영수증은 다시 예치하거나 중복 입금하지 않는다. 이것은 전체 청지기 함수의 모든 부수효과가 재호출에 멱등이라는 주장이 아니다.

기존 장부 압축은 fundId를 버린다. 이 실증은 예치 게시에 일반 플래그 `retainFundIdentity: true`를 붙이고, 그 게시만 기간 합계와 장기 아카이브 모두에서 fundId를 보존하도록 코어 이음새를 추가했다. 기존 플래그 없는 게시의 압축 모양은 그대로다. 저장 검증은 계약별 balance와 **그 fundId만의** 장부 합이 정확히 일치하는지 대조한다. 무관한 murage 기금으로 위조 예치 잔액을 받쳐도 거부한다.

실증은 장부 원시 항목이 모두 장기 아카이브까지 압축된 뒤 저장 복원하고 합의종결된 계약의 잔액을 한 번만 해제한다. 중재 만료·중재자 사망으로 계약이 expired가 되어도 돈은 남는다. 양측이 새 `escrow_release_consent`를 각각 주면 예정된 영주 반환을 실행할 수 있으므로 기한 이후 영구 동결하지 않는다. 한쪽만 동의하면 해제하지 않는다. 종료되고 잔액이 0인 과거 예치는 같은 영지의 다음 별도 소송 예치를 막지 않는다.

## 4. 현재 한계와 채택 전 조건

- 지원 수입은 **영주가 권원과 점유를 모두 가진 지도 밖 전체 영지의 청지기 분기 수입**뿐이다. 본거지 세금·개별 권리 조각·착복 회수·청원 지급·상대 가문의 수입은 대상으로 만들지 않았다. 연가치를 실제 수입이라 하지 않는다.
- 예치의 해제 수령자는 영주만 지원한다. 상대 지급·분배 합의·재판에 의한 강제 해제는 추가 계약이 필요하다. 만료·사망 뒤에도 새 양측 동의로 영주 반환은 가능하며 자동 동의나 자동 해제를 만들지 않는다. 따라서 미결 예치가 있는 모듈 제거는 지원하지 않는다.
- 상대 당사자의 동의 명령은 별도로 입력된다. NPC 자율 수락 생산자·플레이어 권한을 판별하는 외부 명령 라우터·UI는 없다. 시험은 양측 명령을 각각 명시한다. 실제 플레이 중 양측 동의가 자연히 발생했다고 주장하지 않는다.
- 계약은 현재 한 소송에 한 번, 한 영지에 동시 미결 예치 하나로 제한한다. 종료/반환을 마친 과거 계약은 새 소송을 막지 않는다. 과거 계약 재개·교체·취소·정리 정책은 후속 계약이다.
- 시간 순서: 현재 tick 파이프라인은 소송 진행 뒤 청지기 수입이다. 같은 경계에 종결되면 이후 수입은 예치하지 않는다. 기한 당일 종결 동의가 갖춰져 있어도 만료가 우선한다.
- 영수증·연대기의 전용 문구, 선택 성공/거부 읽기 모델, UI 소비, 레지스트리 명령 등록은 후속 작업이다. 일반 소송 단계 기록과 금전 장부는 남지만 완성된 135 플레이 경험은 아니다.
- 195의 source_date 등 모든 편집 차단은 유지한다. RegistryOccurrence(400개 한도), 혼인 PromiseRecord, kind/weight/tick뿐인 Evidence를 계약 저장소로 전용하지 않았다.

## 5. 실증 관문과 증거

`tests/mediationPrototype.test.ts`와 `tests/moduleSlotPrototype.test.ts`는 실제 새 게임/소송 생성, 계절 진행, 실제 청지기 수입, 저장 코덱, 장부 압축을 호출한다. 모의 소송 진행기나 가짜 수입 함수를 사용하지 않는다. 상태 준비와 계절 시각 설정을 사용한 통합 시험이며 자연 플레이 관측은 아니다.

Mac에서 전용 20개와 기존 suitActions 2개, 브라우저 안전 이행 2개: **24/24 통과**. 확인한 경계: 미확인 모듈, 미래 판, 팩 불일치, 변형 데이터, v54 무효과 이행, 실제 소송 유예/만료/종결, 독립 동의, 부적격 중재자, 무허가 제삼자, 실제 수입 보존, 별도 예치 동의, 압축/복원/한 번 해제, 만료 뒤 양측 반환 동의, 무관한 기금에 기대는 위조 잔액 거부, 후속 별도 소송 예치, 빈 슬롯/슬롯 부재 동등성, 읽기 모델의 유예 기한.

추가 형식/빌드 검증 결과는 `docs/requests/engine-B-mod-slot.md`에 기록한다. 장기 결정론·전체 회귀·가드레일·자연 빈도·UI·사람 플레이는 실행하지 않았다. 이 증거는 실증 이음새의 계약 검토 근거이며 본선 게시 관문을 대신하지 않는다.
