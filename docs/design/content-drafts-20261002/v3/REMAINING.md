# 남은 문제와 엔진 인계

1. **LM-E9 보고서 확인 불가.** 지정 브랜치를 갱신하며 `docs/verification/lm-e9/AMBIGUOUS.md`를 확인했으나 현재 작업 스냅숏에는 없다. 사용자 지정 목록의 15개만 수정했다. 따라서 미등록 24개 전체나 그 밖의 “Astra 확인” 항목을 해결했다고 주장하지 않는다. 확인 시각·HEAD는 `records/source-snapshot.json`에 기록한다.
2. **등록기 바인딩은 엔진 몫.** 실제 영지·청지기·감사·길드 인물 및 건설 후보를 선택하고 조건을 허용 목록 predicate에 연결해야 한다. 수치 문턱을 확정했지만 이번 JSON 자체가 실행 가능한 LM-E9 정의라고 주장하지 않는다. 없는 필드/대상/선택은 추측으로 보충하지 말고 카드를 생략한다.
3. **복합 선택.** 004·030·049의 분할 장려금은 기존 명령 두 개다. v2의 `sequential_non_atomic` 명세를 유지한다. 등록기 정책이 원자적 어댑터를 요구하면 어댑터 구현 전 분할 선택을 비활성화하고, 실행 가능한 선택이 둘 미만이면 카드를 숨긴다. 첫 명령만 성공한 것을 전체 성공으로 기록하지 않는다.
4. **기간·최초 위임 이력.** 일반 공사가 목재를 기다린 일수는 확인 가능한 공통 필드가 없어 사용하지 않았다. 현재 수요와 재고로 판정한다. 059는 현재 직접 감독→위임의 문맥이다. 생애 최초 위임인지의 엄격한 판정은 현재 모드만으로 알 수 없으므로 발생 이력/중복 억제는 등록기 책임이다.
5. **가용성과 균형.** 008의 거리 문턱은 콘텐츠 기준이며 채플의 서비스 반경이 아니다. 엄격한 실제 후보·금고·인물 조건은 노출 빈도를 낮출 수 있다. 다양한 저장 상태에서의 도달 빈도, LM-E9 노출·클릭·저장/복원·이중 클릭·마감 직전 재검사는 엔진 통합 뒤 검증할 사항이다. 이번에는 게임 실행 검증을 하지 않았다.
6. **후처리와 유지 선택.** 감사 처벌의 연결 세력 관계 효과는 `answerAudit`만으로 끝나지 않고 `history.ts`의 후처리를 거친다. 등록기가 미리보기 수치를 다시 더하면 이중 적용이다. 019·059의 직접 감독 유지, 015·035의 주문 보류, 046의 주문 유지에는 상태 변경을 꾸며 붙이지 않는다.

후속 엔진 작업을 대신 구현하거나 저장소에 콘텐츠를 설치하지 않았다.
