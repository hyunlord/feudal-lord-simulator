# 누적 원고의 중복 억제 통합 계약

상태: 등록기 구현 제안. 엔진 설치·저장 재개 검증 없음. 현재 원고의 모든 `enabledInEngine=false`는 유지한다. 이 문서가 미지원 생활 문제나 새 효과를 구현해 주지는 않는다.

## 단일 정의와 충돌

한 canonical group ID의 회원 목록·키·반복 규칙은 중앙 계약에서 한 번만 정의한다. 같은 이름에 서로 다른 목록이 발견되면 자동 합집합·마지막 파일 우선으로 덮지 않고 병합을 차단한다. 원고에는 계약 ID/ref만 둔다. 본문이 비슷하거나 같은 명령을 쓴다는 이유만으로 같은 생활 문제라고 정하지 않는다.

교회·이웃 `dedup-contract.json`의 `marriage.candidate_pair.v1`은 기존018과 새6건을 실제 신랑·신부 ID에 연결한다. 원018의 없는 `bound.instanceId`를 그대로 쓰지 않는다. 이 교차군은 캠페인/후보쌍 키이며 다른 실제 후보쌍을 같은 키로 만들지 않는다. 혼인 엔진 자체의 일회 제약은 별도로 적용된다.

세력·자연의 근접 원고군은 해당 폴더 중앙 계약의 실제 소송·청지기·기존 발생 또는 명시적 생활 문제 맥락을 따른다. 필요한 problemCaseId가 현재 엔진에 없으면 등록기 어댑터 미지원으로 차단한다. 목재 주문이라는 명령 이름만으로 모든 목재 청원을 평생 하나로 합치지 않는다.

교회·이웃 civic token 계약은 **추가 상담의 노출 간격**이며 실제 사건의 동일성을 증명하는 키가 아니다. 겹치는 명령 토큰 때문에 기존 청원·장 사건을 취소하지 않는다. 서로 다른 조절 계층이 함께 적용된다면 생활 문제 중복 판정 뒤 추가 상담 cooldown을 적용한다. 어느 계층에 필요한 맥락이 없더라도 원래 엔진 발생은 그대로 둔다.

## 처리 순서

1. 원래 엔진이 만든 발생 ID와 기한·당사자·효과 주체를 먼저 확보한다. 기존 사건의 arrival을 새 등록기 예산이나 dedup으로 지우지 않는다.
2. `existing_petition_variant`는 **그 동일 발생의 표시문구**를 선정한다. 별도 occurrence·새 기한·새 선택 실행을 생성하지 않는다. 동일 occurrence 자신의 pending 예약은 문구 선정을 막지 않는다. 다른 발생의 예약은 무시하지 않는다.
3. `new_event_draft` 후보는 현재 실제 대상·필수 조건·의미 있는 선택2개·미지원 차단을 검사한다. 유효한 canonical context key를 만들 수 없으면 그 추가 원고만 숨긴다.
4. 같은 canonical key의 다른 열린 발생을 억제한다. 해결된 키는 해당 중앙 계약의 재등장 규칙을 따른다. once 규칙이면 영구, cooldown이면 기한과 실제 후속 상태 변화를 모두 확인한다.
5. 새 카드를 실제 노출할 때 예약을 저장한다. 선택 뒤 현재 상태를 다시 검사하고 엔진 명령을 정확히 한 번 실행한다. 원자 실행이 없는 묶음은 계속 차단한다. dismissal이 원래 기한을 연장하지 않는다.
6. 예약·해결 상태·키 버전·발생 ID는 등록기 저장 모형에 함께 남아야 한다. 현재 GameState에 그런 필드가 있다고 주장하지 않는다. 구 저장의 대상 식별자를 복원할 수 없으면 해당 추가 변주를 차단하고 원래 게임 사건은 유지한다.

## 경량 계약 예제의 범위

`records/registry-dedup-reference.mjs`는 위의 단일 그룹/같은 발생 예외/필수 키 처리만 순수 데이터로 검사한다. 게임의 난수·조건 평가·명령·저장 codec을 실행하지 않는다. 통과를 실제 등록기 구현·150년 노출 빈도·균형의 증거로 삼지 않는다. 캠페인당1회라는 엄격한 예제는 모든 사건의 기본 반복 규칙이 아니다.
