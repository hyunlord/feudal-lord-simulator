# 서버 비용·확장성 갱신 — 원본 엔진 측정 반영

2026-10-06 / R03. 읽은 증거: [기존 플랫폼 조사](PLATFORM_RESEARCH.md), [벤치마크 판정](evidence/BENCH_RESULT.md), [원본 측정 JSON](evidence/engine-bench.json). 이 문서는 측정 결과의 비용상 의미를 보완한다. 기존 파일·엔진 코드를 바꾸거나 벤치마크를 재실행하지 않았다.

**기존 월 $5.80/$55.13은 단순화한 정산기가 가정한 CPU·저장량 안에서 실행될 때의 edge 서비스 산식이다. 원본 PC 엔진의 월 운영비로 적용할 수 없다.** 기존 `오프라인 정산 4회×20ms/일`은 연구 단계의 가정이며 실제 PC 엔진의 오프라인 catchup 측정값이 아니다. 현재 관찰된 catchup은 full tick 100회를 그대로 반복한 107.413~135.388ms다. 이벤트 건너뛰기 방식이 같은 결과를 내거나 20ms에 정산을 끝낸다는 증거는 없다.

## 관찰과 해석의 경계

- Apple M4 Max / Node v25.8.2의 단 한 번 실행이다. 400개 측정 tick에서 phase 평균은 1.073~1.771ms/tick, opening 최대는 164.020ms였다. 아래에서는 평균 범위를 둥글게 `w=1.07~1.77ms/tick`으로 쓴다. 이것은 신뢰구간·최악 상한·미래 성장 예측이 아니다.
- 시간은 데스크톱 **경과 시간(wall time)** 이다. 서버의 process CPU time이나 공급자의 청구 CPU ms를 측정하지 않았다. 평균을 장기간 선형 외삽한 수치는 용량 검토용 가설이다. 짧은 mature fixture에는 Lord agency·diplomacy가 없었고 연간 estate/계절 suit도 실행되지 않아 장기 Lord Mode 부하를 대표하지 않는다.
- tick 이후 프로세스 RSS는 약 322/342MB, mature 저장 이후 약 368MB였다. Node 런타임·imports·캐시·직전 사례 할당을 포함한 공유 프로세스 값이며 강제 GC나 격리 측정이 없다. 이를 한 영지의 상주 메모리로 곱하지 않는다.
- Workers의 메모리 한도는 **isolate당 128MB**이며 요청마다 별도 128MB가 아니다. RSS와 isolate heap/allocation은 서로 다른 지표라서 RSS>128MB만으로 배포 불가능이 증명되지는 않는다. 반대로 현재 자료로 원본 엔진이 Workers에 들어간다고 주장할 수도 없다. 번들·런타임 호환, isolate 메모리 최고값, 동시 요청과 저장 직렬화의 추가 할당을 대상 런타임에서 검증해야 한다. [공식 Workers 제한](https://developers.cloudflare.com/workers/platform/limits/), 2026-10-06 확인.

## 틱 빈도가 바꾸는 연산량

`A`는 **매일 진행시킬 전체 영지/계정 수**다. 아래의 A=1,000/10,000이 DAU와 같으려면 그날 활동한 계정만 진행시킨다는 정책이 필요하다. 휴면 계정도 매일 진행하면 A는 DAU보다 커진다. 로그인 때 밀린 tick을 처리하더라도 총 tick을 줄이지 않으면 연산을 나중으로 미룰 뿐이며, 재접속 순간 backlog가 몰릴 수 있다.

- `T`: 계정당 하루 진행 tick. 분당 1tick이면 1,440, 초당 1tick이면 86,400.
- `k`: 동일 tick당 서버 worker 경과 시간이 데스크톱 측정의 몇 배인지 나타내는 **미측정 서버 배율**. 아래 k=1/3은 민감도 예시다. k=3이 안전 상한이라는 뜻은 아니다.
- 월 serial-worker service시간 환산 `H = 30 × A × T × w × k / 3,600,000`시간.
- H는 순차 실행 경과 시간의 합을 외삽한 값이다. **청구 CPU시간이 아니며**, IO·저장/로드·GC·시작 비용·습격·인증·DB·재시도 부하는 포함하지 않는다.

| 진행 정책 | A | 월 H, k=1 | 월 H, k=3 |
|---|---:|---:|---:|
| 분당 1tick | 1,000 | 12.84~21.24시간 | 38.52~63.72시간 |
| 분당 1tick | 10,000 | 128.40~212.40시간 | 385.20~637.20시간 |
| 초당 1tick | 1,000 | 770.40~1,274.40시간 | 2,311.20~3,823.20시간 |
| 초당 1tick | 10,000 | 7,704~12,744시간 | 23,112~38,232시간 |

분당 tick은 초당 tick보다 위 산식에서 60배 적다. 그러나 tick이 나타내는 게임 시간을 바꾸면 생산·이동·이벤트 발생의 제품 규칙도 달라질 수 있다. 이것을 의미 보존 최적화로 취급하지 않는다. 원본 틱 의미를 유지하는 이벤트 skip/집계 적분은 별도 동등성 검증 전까지 비용 절감에 반영하지 않는다.

1일 누적분을 한 번에 따라잡는 경우 k=1의 단순 외삽 경과 시간은 분당 정책에서 약 1.54~2.55초, 초당 정책에서 약 92.45~152.93초다. k=3이면 각각 약 4.62~7.65초, 277.34~458.78초다. 모두 실제 1일 실행 결과가 아니며 초기화와 저장 비용도 빠져 있다. 동기 API 응답으로 기다리게 하기보다 큐·상태조회와 bounded chunk를 검토할 근거다.

## 원본 엔진을 유지하는 제품 구조

권장 검증 경로는 **인증/API → 권위 DB의 명령·outbox → 큐 → 독립 Node 연산 worker → snapshot/결과 원장 → API 조회**다. Node는 이번에 로컬 실행을 확인한 런타임이라는 의미이며 특정 클라우드에서 구현·배포했다는 뜻이 아니다. edge API는 인증·입력 제한·명령 접수 역할로 두고 원본 엔진을 edge isolate에 즉시 넣는 것을 전제하지 않는다.

worker는 영지별 revision/lease와 idempotency를 확인하고 snapshot 버전부터 제한된 tick 묶음을 진행한다. 명령/결과 ledger와 완료 snapshot 포인터를 정합하게 반영한 뒤에만 queue ack한다. 중복·역순·worker 종료를 견뎌야 한다. 큐에 전체 save를 넣지 않고 ID와 snapshot reference를 넣는다. 큐의 최소 1회 전달과 순서 비보장 때문에 이것이 필요하다. [전달 보장](https://developers.cloudflare.com/queues/reference/delivery-guarantees/), [큐 동작](https://developers.cloudflare.com/queues/reference/how-queues-works/).

초당 지속 실행과 재접속 catchup은 같은 큐에서 무제한 경쟁시키지 않는다. 시즌 마감·공격 도착·복귀 유저의 우선순위, 최대 누적 시간, 처리 지연의 UX를 먼저 정한다. 캐시를 영구 정답으로 쓰지 않고 재시작 시 저장된 checkpoint에서 재개한다. 공격자/방어자 자원을 바꾸는 정산은 원자성 경계를 설계해야 하며 worker를 분리했다는 사실만으로 중복 보상 문제가 해결되지는 않는다.

## 비용 산식과 아직 넣을 수 없는 단가

배포 공급사·리전·인스턴스·사용률이 정해지지 않았으므로 Node compute의 실제 달러 견적은 **미확정**이다. 데스크톱 H에 Workers CPU 단가를 곱하지 않는다.

상시 예약 방식의 예시 산식은 다음과 같다.

- `u`: worker가 게임 연산에 쓸 목표 점유율(예: 0.5는 운영 여유를 절반 남기는 설계 가정).
- `s`: 목표 인스턴스에서 실제 검증한 병렬 serial-worker slot 수. vCPU 수와 자동으로 같다고 간주하지 않는다.
- `n = max(n_min, ceil(H / (720 × u × s)))`.
- `월 compute 비용 = n × 720 × p_instance_hour`.
- 최종 n은 위 평균 처리량 계산뿐 아니라 메모리·peak backlog 복구 시간·고가용성 조건을 만족해야 한다. 로드/저장/전투 등 추가 시간을 반영한 H로 재계산한다.

예를 들어 k=3, u=0.5, s=1, n_min=1의 가정에서는 분당 정책 A=1k가 1개, A=10k가 2개 slot-equivalent 인스턴스이고 초당 정책 A=1k가 7~11개, A=10k가 65~107개다. 이는 **특정 VM 필요 대수나 실제 요금의 확정값이 아니다.** 서버 실측과 slot당 메모리·가격이 빠진 규모 감도다. 과금형 container를 선택하면 공급자의 청구 vCPU-second·GB-second·idle/minimum charge에 맞춰 별도 산식을 써야 한다.

전체 월비용은 `인증/API + 큐 + Node compute + DB + snapshot storage/operations + 네트워크 + 관측/백업`이다. 예시 세부식은 다음과 같다.

- 정산 job이 계정당 하루 J개이고 정상 완료 메시지가 64KB 이내라면 Queue operations는 대략 `30×A×J×3 + retry/DLQ 추가량`. tick마다 job을 만든다고 가정하지 않는다. job을 합쳐도 동일 full tick 연산량 자체는 줄지 않는다. [Queues 과금](https://developers.cloudflare.com/queues/platform/pricing/).
- snapshot 평균 크기 B bytes, 보관 snapshot 수 K/계정이면 대략 `A×B×K/1e9`GB와 업로드/다운로드 연산 수를 계산한다. mature 저장은 **4,895,144 bytes**였으므로 A=10k에 snapshot 한 개씩만 보관해도 약 48.95GB다. 기존의 DB 20GB 가정과 동치가 아니며 큰 저장 본문은 object store, DB에는 권위 metadata/원장을 두는 분리를 검토한다.
- 하루 J회 전 계정 snapshot을 로드한다면 읽기량은 `30×A×J×B/1e9`GB다. A=10k, J=4, mature B의 가정이면 월 약 5,874.17GB다. 캐시·압축·delta를 적용하지 않은 산술치이며 API 응답에 전체 snapshot을 매번 보내야 한다는 뜻은 아니다. R2 egress가 무료여도 별도 Node 공급사의 네트워크·게이트웨이·요청 비용까지 무료인 것은 아니다. [R2 요금](https://developers.cloudflare.com/r2/pricing/).

기존 Workers $5 기본, 요청 초과 100만당 $0.30, CPU 초과 100만 ms당 $0.02 산식은 **가벼운 API 또는 별도 단순화 모델의 실측 CPU량**에만 조건부 적용한다. 무료 포함량은 계정 내 다른 작업과 공유하므로 두 모델에 중복 적용하지 않는다. [Workers 공식 요금](https://developers.cloudflare.com/workers/platform/pricing/). 기존 연구의 $5.80/$55.13을 위 Node 구조 비용에 그대로 더하면 API/queue/storage가 중복 집계될 수 있으므로 항목별로 다시 쓴다.

최종 견적에는 계정 총수와 휴면 정책, 리전, 서버 CPU/메모리 최고값, 목표 복귀 지연, peak 동시성, 저장 보존기간, 인증·로그·백업, 장애 여유를 넣어야 한다. 현재 수치에는 인건비·온콜·보안 운영, 세금·환율, 스토어 계정/수수료, QA/스테이징, 도메인, 이메일/SMS와 별도 공급사 네트워크 요금이 포함되지 않았다. **현재 통과한 것은 로컬 엔진 재사용의 작은 실행·저장 관문이며, 원본 엔진의 저가 edge 배포나 10k DAU 운영 승인 관문은 아니다.**

## 공식 가격을 붙인 조건부 compute 예시

2026-10-06 확인한 [DigitalOcean 공식 가격](https://www.digitalocean.com/pricing/droplets)은 CPU-Optimized Regular 2vCPU/4GiB를 시간당 $0.06250, 월 상한 $42로 제시한다. 이 예시는 해당 VM을 구매하거나 벤치마크한 결과가 아니다. 두 vCPU라고 두 slot을 인정하지 않고 앞 표의 가정 s=1, k=3, u=0.5를 그대로 대입한다. 한 달 내내 유지하면 시간 단가×720 대신 월 상한을 적용한다.

| 조건 | 가정상 인스턴스 수 | compute만의 월 예시 |
|---|---:|---:|
| 분당1tick, A=1k | 1 | $42 |
| 분당1tick, A=10k | 2 | $84 |
| 초당1tick, A=1k | 7~11 | $294~462 |
| 초당1tick, A=10k | 65~107 | $2,730~4,494 |

이 가격표는 **공식 단가에 미검증 용량 가정을 곱한 민감도 예시**다. 이 VM에서 k=3과 s=1이 성립한다는 증거는 없으며 실제 서버 견적 범위나 상한도 아니다. DB·API·큐·저장·네트워크·백업·예비 용량·운영 인건비가 빠져 있다. 기존 edge 월$6/$55와 합치면 중복 항목을 만들므로 합산하지 않는다. 전체 운영비는 여전히 미확정이다. 다만 “틱 빈도가 비용을 크게 바꾼다”는 의사결정에 달러 크기를 연결한다.
