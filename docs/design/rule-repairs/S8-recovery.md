# S8 자동 성장 자재·밀 운송 복구

## S8-F1 / R-7 목재 확장

목책·석벽에 남은 목재 수요가 있고 가용 목재가 기존 자동 성장 비축 기준 120 미만인 상태를 2,400틱 연속 관측한다. 생산 시설 공사 중에는 이 관측을 초기화하여 완공 뒤의 결과를 먼저 본다. 최근 실제 생산보다 남은 공사 수요가 큰 경우, 제재소가 실제 원목을 가져오는 창고의 미예약 재고를 본다. 기존 제재소의 다음 1회 생산에 부족한 원목을 먼저 충당하고 운반 한 짐 이상이 남으면 제재소, 아니면 벌목소를 한 곳 확장한다. 각 제재소의 현재 가용 투입 재고와 도착 예약 원목은 기존 부족분에서 공제한다. 투입량과 한 짐은 기존 생산 명세와 `CARTER_CAPACITY`를 사용한다. 건설비·가용 인력·창고 여유·기존 서비스 공간과 성벽 여유 검사는 그대로다. 기존 코드에는 목재 시설 수량 상한이 없다. 새 주택-시설 비율을 만들지 않고 공사 한 건·완공 후 재관측·실제 인력과 생산 여유로 증설을 제한한다. 기존 식량 시설 상한은 변경하지 않는다.

연속 부족 시작 시점은 저장하는 선택적 관측값이다. 구형 저장에는 과거 관측을 발명하지 않고 첫 실제 부족 틱부터 시작한다.

## S8-R8 추가 조항 / 밀 운송 막힘

A⁵-1 seed 1 원본(tick 1,200,000)은 곡창 7개로 상한에 도달했고 먼 곡창 여럿에 밀 100·빵 0이 쌓였다. 방앗간 7개는 모두 원료가 있지만 최근 2,400틱의 원료 부족 시간은 1,814/16,800, 빵 생산 501·요청 481·판매 17이었다. 이 상태에서 곡창만 추가하려는 기존 복구는 항상 `none`이었다.

1. 기존 경로 복구·곡창 복구를 먼저 유지한다.
2. 완전한 2,400틱 실측 창에서 원료 부족 시간이 있고 빵 여유가 부족하면, 밀 재고가 한 짐 이상인 곡창에서 가까우면서 빵이 빈 주택까지의 실경로가 짧은 방앗간 자리를 최대 24개 검사한다.
3. 기존 방앗간 하나라도 밀 0이면 증설 금지, 방앗간≤밀밭, 반복 실패 억제·인력·자재·성벽·서비스 공간 검사를 모두 유지한다.
4. 선택 조치를 진단 `transport_capacity_selected`와 실제 건물·좌표로 남긴다. 건설·생산·운송 수치나 게임 규칙은 바꾸지 않는다.

원본 gzip fixture는 `tests/fixtures/autoplay-recovery/`에 SHA와 출처를 보존한다. 수정 전 원인/조치 없음 재현 → 행동 테스트 실패 → 복구 구현 순서로 진행했다. 전체 `decideNextAction` 우선순위·탐색 예산과 실제 엔진을 함께 24,000틱 재생했다. 처음 모든 집에 빵이 생긴 시점은 +751틱, 최종 빵 0 집 0개였다. 방앗간7→10·밀밭21→22·곡창7로 기존 상한을 유지했다. 이 시험은 자동 성장 자연 상태의 재생이며 화면 플레이가 아니다.

## R-7 검증

### 후속 자연 상태 반례와 선택 수정

후속 seed 1 자연 진행의 갱신 중 상태를 별도 복사한 실제 시점은 144,000틱이며 제재소 18·벌목소 3이었다. 많은 제재소가 원목 0 또는 1이었고, 창고의 원목은 모두 운송 예약 상태였다. 기존 선택은 제재소 투입 재고·벌목소 출하 전 재고까지 도시 전체에서 합쳐 추가 제재소가 쓸 여유로 오인했다. `availableStock`의 예약 공제 자체는 정상이었다.

그래서 실제 반입 출처인 창고 자유 재고와 기존 생산 투입 부족분을 구분했다. 작은 회귀에서 분산 투입 원목 8·창고 원목 9 전량 예약 사례, 빈 제재소 1개·자유 원목 8 사례가 수정 전 잘못된 제재소 선택으로 실패했고 수정 후 벌목소를 선택했다. 자유 원목 10에서 기존 생산 2를 충당한 뒤 한 짐 8이 남는 경우, 기존 생산 2가 이미 도착 예약된 경우, 기존 자유 원목 80 사례는 모두 제재소 선택을 유지했다. 목재 선택·저장 집중 테스트 9개가 통과했다. 이 결과는 선택 규칙 검증이며, 수정 후 자연 진행·전체 회귀·성능 재검증은 별도 게이트다.

### 이전 선택 규칙의 자연 진행 기록

기본 새 게임에서 실제 자동 성장·120틱 결정 주기로 120,000틱 진행했다. 확장은 53,400틱 벌목소, 57,480틱 제재소, 62,880틱 벌목소였다. 목책 완공은 60,000틱 1/20 → 72,000틱 6/20 → 84,000틱 10/20 → 96,000틱 14/20 → 108,000틱 16/20 → 120,000틱 18/20. 기존 S0 탐침은 같은 상한에서 벌목소 1·제재소 1, 목책 12/18이며 둘레 개수 차이는 이번 다른 규칙 수정도 함께 작용한다. 순수 R-7만의 속도 향상치라고 표현하지 않는다.

저장 스키마 v4의 선택 필드 `timberProductionWindow.expansionShortageSinceTick`은 매 실제 틱 관측을 유지한다. v3→v4는 이전 상태를 그대로 보존한다. 지문용 `timber-shortage.save.json`은 기존 자연 목책 저장 90,976틱을 정상 엔진으로 1,708틱 진행해 처음 부족이 나타난 92,684틱에 저장했다. 자원 주입·배치 편집 없음.
